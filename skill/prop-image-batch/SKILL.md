# 道具图批量修图

所有命令使用本文件旁的 `scripts/batch.py` 的**绝对路径**。下文用 CLI 代指该路径。无需项目仓库。工作区默认是当前目录下的“道具修图工作区”；需要指定时在子命令前添加 `--workspace "目录"`。续跑沿用同一工作区。不要把原图库或 Skill 安装目录用作输出目录。

手动操作见[从安装到验收入库](references/usage.md)。

**安装、配置或求助**：仓库中的安装目录是 `skill/prop-image-batch`。先识别操作系统，找到 Python 3.9+，运行 `python -B CLI check-install`。缺依赖则按[首次配置与常见问题](references/setup.md)补齐后复查。服务配置缺失时先问“你用的是团队提供的图像服务，还是自己开通的服务？”，已有答案就直接使用。按对方的服务和系统给当前这一步能照做的指引：找谁领地址和模型、在哪个窗口填写、怎样在本机输入密钥。不要只列变量名或只丢文档链接，不索取或显示密钥。

用户完成设置后运行 `python -B CLI doctor`，分别告知“可否预检”和“出图是否实际验证”。只配置不提交图片；只有用户要求试跑，且服务确实返回了有效透明 PNG，才报告“已验证能出图”。请求失败时按指南对应错误答疑。

**更新流程**：开始新批次前可自动执行 `python -B CLI check-update`，只报告本地版本、远端版本和提交摘要，不修改文件。用户明确说“更新”后才执行 `python -B CLI update`，更新完成后重跑 `check-install` 和 doctor。更新只替换 Skill 安装目录；本机环境变量、原图库、工作区、批次和正式成品都在安装目录之外。

只上传当前道具的 RGBA 副本，等比采样至短边 2048；提示词填写游戏原宽高。通过已配置的网关请求 2048×2048 透明 PNG；实际返回宽高以解码为准，最终恢复原尺寸。画风只由提示词控制，示例图不上传。 默认使用 `gpt-image-2.5-sunburst`、`quality=high`。直接运行随包入口，无需通用生图 CLI。验证运行路径时，只需确认请求成功、原始 PNG 落盘、恢复到原尺寸；外观和轮廓另行验收。

**运行请求**：取得明确的原图库目录和起止组号。“前三组”是 1–3。只从指定目录顶层取原图，不搜索替代目录。
1. 执行 `python -B CLI preflight --start 1 --end 3 --source-dir "原图库"`（替换实际参数）。失败就停止；用户只要求预检时到此结束。
2. 新批次用相同参数执行 `init`，记下输出的绝对批次路径；续跑核对 meta.json 的范围与原图库后，继续已有批次。执行 `submit "批次"`，再执行 `restore "批次"`。只上传对应原图和正式提示词。本组代表图未被人工放行不继续提交。
3. 用批次内的复核.html 和恢复核验.json 展示原图与恢复稿。技术未过、返回不透明或请求状态不明时暂停；不改原图文件，恢复稿保留生成稿 RGB，先检查对位（主体重叠率低于 0.85 待复核），再使用原图 Alpha 作为最终透明边缘与镂空，不自动重发。依照 [批量规则](assets/01_规则与提示词/批量运行规则.md) 和 [验收标准](assets/01_规则与提示词/图片编辑与验收规则.md) 按组检查。
4. 人工确认后 `accept "批次" 文件名...`；退回用 `reject "批次" 文件名... --reason "原因"`。每组作为一个节点。用 `checkpoint "批次" --group N` 列出应检查的样本。首组全检达 90%，以后抽 20 张达 19/20；不足 20 张全检达 90%。处理全部异常、人工确认无共性问题后加 `--no-common-issue` 放行该组。用户明确要求入库时才 `publish "批次" 文件名...`。不覆盖同名成品。`status "批次"` 可查台账，`meta.json` 的状态依次记录 `prepared`、`submitting`、`submitted`、`review`、`accepted`、`published`。
